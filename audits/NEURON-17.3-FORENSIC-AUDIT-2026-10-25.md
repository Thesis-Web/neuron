## Your question first: does mother ever hit the SQL prompt, and how do new neurons appear?

New neurons are real SQLite tables. But the brain never composes them. In 17.3:

1. A new word is born by the hand-laid trigger `born_go` (SQL:781-789). The CREATE text is a string template inside that trigger: `SELECT mother('CREATE TABLE g' || gate || ' (shard INTEGER PRIMARY KEY, arrival INTEGER, …)', NULL, NULL)`, then the same for `CREATE VIEW land_…` and `CREATE TRIGGER miss_…`.
2. `mother` is a function the host registers into SQLite (PY:10, HTML:696) and runs on the spot (PY:39). When she is called with run = NULL, as every birth, lay and landing is, she writes **no event row**: PY:47-50 "a by-value step of the physics itself (a birth, a lay, a landing): the SQL prompt's own answer goes straight back". That is why the page shows tables appearing with no "mother carries it to the SQL prompt" step. I made those calls silent.
3. The same template mechanism writes every DNA row and its hop trigger (`lay_go` SQL:822-823), the `:prev` row (SQL:816), the bind (SQL:843-844) and the step-back (SQL:965).
4. Only two paths do it your way, a run of neurons assembling text that mother pastes: a taught formula's statement ending at `;` (SQL:823 → `stmt_go` SQL:865) and a typed `BUILD … BUILD` line (SQL:994, 1026). Those are the paths the Step log shows going to the SQL prompt.

v1 had the same split: `g3` born a neuron from a template inside the trigger (egg.sql:19), and `g5` ended a `BUILD … BUILD` run by handing the heard words to mother (egg.sql:21). You said it on 10-20 (§0): "THE RUN THAT LAYS THE CODE TO TALK BACK TO SQL IS THE MOST CORRECT WE HAVE... THE TABLES ARE BUILT WRONG THOUGH BECAUSE YOU DEEMED TO AN ENGINEERING CHANGE". 17.3 kept the wrong half and hid it.

So: not fake SQL, but a template the brain never ran, executed by a host function that logs nothing. The one piece that would let you fix things, the born run, does not exist in 17.3. It is row 3 below.
